---
title: "execute_sql"
---

Execute SQL queries and statements on your database with support for transactions, multiple statements, and safety controls.

## Parameters

- `schema` (required): Target schema for this query. Cross-schema SQL is rejected even when PII or destructive overrides are enabled.
- `sql` (required): SQL to execute (multiple statements separated by `;`)

## Features

- **Single statements**: Execute a single SQL query or command
- **Multiple statements**: Separate multiple statements with semicolons (`;`)
- **Transactions**: Wrap operations in `BEGIN`/`COMMIT` blocks for atomic execution
- **Read-only mode**: When enabled with `--readonly` flag, only SELECT and read-only operations are allowed
- **Row limiting**: Configure `--max-rows` to limit SELECT query results
- **PII/clinical guard**: Clinical/health data (HL7v2, FHIR, LOINC, SNOMED, medical fields), wildcard projections (`SELECT *` / `table.*`), and personal & sensitive data (names, email, government/financial IDs, DOB/age, address/location, biometric/device IDs, demographics, credentials/secrets) are **hard-excluded** and can never be returned. The **only** overridable field is the user's mobile/phone number (the Helium username), opted into per tool (see below)

## Single Query

Execute a single SELECT, INSERT, UPDATE, or DELETE statement.

<CodeGroup>
```sql SELECT
SELECT * FROM users WHERE status = 'active' LIMIT 10;
```

```sql INSERT
INSERT INTO users (name, email) VALUES ('Alice', 'alice@example.com');
```

```sql UPDATE
UPDATE users SET last_login = NOW() WHERE id = 123;
```

```sql DELETE
DELETE FROM sessions WHERE expires_at < NOW();
```
</CodeGroup>

## Multiple Statements

Execute multiple SQL statements in sequence by separating them with semicolons.

```sql
INSERT INTO users (name, email) VALUES ('Alice', 'alice@example.com');
INSERT INTO users (name, email) VALUES ('Bob', 'bob@example.com');
INSERT INTO users (name, email) VALUES ('Charlie', 'charlie@example.com');
```

<Note>
Each statement is executed sequentially. If one statement fails, subsequent statements may not be executed depending on the database error handling.
</Note>

## Transactions

Wrap multiple operations in a transaction to ensure atomicity. Use `BEGIN`/`COMMIT` for successful transactions or `ROLLBACK` to undo changes.

<CodeGroup>
```sql Successful Transaction
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

```sql Rollback Transaction
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Something went wrong, undo changes
ROLLBACK;
```
</CodeGroup>

## DDL Operations

Create, alter, or drop database objects.

<CodeGroup>
```sql CREATE TABLE
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  price DECIMAL(10, 2) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

```sql ALTER TABLE
ALTER TABLE products ADD COLUMN category VARCHAR(100);
```

```sql CREATE INDEX
CREATE INDEX idx_products_category ON products(category);
```

```sql DROP TABLE
DROP TABLE IF EXISTS temp_data;
```
</CodeGroup>

## Read-Only Mode

Restrict SQL execution to safe, read-only operations by configuring the `execute_sql` tool with `readonly = true`:

<CodeGroup>
```toml TOML Configuration
[[sources]]
id = "production"
dsn = "postgres://user:pass@localhost:5432/mydb"

[[tools]]
name = "execute_sql"
source = "production"
readonly = true
```

```bash Command Line (Deprecated)
# This flag is deprecated - use TOML configuration instead
npx electric-elephant --readonly --dsn "postgres://user:pass@localhost:5432/mydb"
```
</CodeGroup>

In read-only mode, only [allowed SQL keywords](https://github.com/bytebase/dbhub/blob/main/src/utils/allowed-keywords.ts) are permitted, including:

- `SELECT` queries
- `SHOW` commands
- `DESCRIBE` commands
- `EXPLAIN` queries
- Other read-only operations

## Row Limiting

Limit the number of rows returned from SELECT queries to prevent accidentally retrieving too much data:

<CodeGroup>
```toml TOML Configuration
[[sources]]
id = "production"
dsn = "postgres://..."

[[tools]]
name = "execute_sql"
source = "production"
max_rows = 1000
```

```bash Command Line (Deprecated)
# This flag is deprecated - use TOML configuration instead
npx electric-elephant --max-rows 1000 --dsn "..."
```
</CodeGroup>

- Only applied to SELECT statements, not INSERT/UPDATE/DELETE
- If your query already has a `LIMIT` or `TOP` clause, Electric Elephant uses the smaller value
- Can be configured per-tool in [TOML configuration](/config/toml)

## PII and clinical data guard

The projection guard has **two tiers**: a hard exclusion covering health/clinical data, personal identifiers, and wildcards — which can never be overridden — and a single overridable field, the user's mobile/phone number (the Helium username), which an operator can opt into.

### Hard exclusion (clinical/health data — cannot be overridden)

Clinical and health data is **always blocked** and can never be returned by this server, regardless of `allow_access_to_pii_data`, `clinical_standards`, or any CLI/env flag. This covers projections that match HL7v2/LIS, FHIR, LOINC, or SNOMED naming, plus medical heuristics (HIV/TB and related markers, blood and lab panels, pathology/chart-note names, diagnoses, medications, etc.).

Wildcard projections (`SELECT *`, `table.*`, `schema.table.*`) are **also hard-excluded**: a wildcard cannot be statically proven free of clinical columns, so it is always rejected — even with `allow_access_to_pii_data = true`. List explicit, non-clinical columns instead.

Examples of hard-excluded naming styles:
- HL7v2/LIS: `hl7messagecontrolid`, `elzId`, `orderID`, `barcode`, `testtype_fields`, `resultForAction`
- FHIR: `subject_reference`, `observation_value`, `condition_code`
- LOINC: `loinc_code`, `loinc_number`
- SNOMED: `snomed_ct_code`, `concept_id`
- Medical heuristics: `hiv_status`, `blood_glucose`, `hemoglobin_a1c`, `chief_complaint`, `diagnosis`

The `clinical_standards` TOML field is retained for backward compatibility, but it **no longer narrows or disables** clinical detection — every clinical standard is always evaluated for the hard exclusion:

```toml
[[tools]]
name = "execute_sql"
source = "production"
# clinical_standards is accepted but does not weaken the hard exclusion
clinical_standards = ["hl7v2", "fhir", "loinc", "snomed"]
```

### Hard-excluded PII (never overridable)

Almost all personal and sensitive data is also hard-excluded and can never be returned. `allow_access_to_pii_data` does **not** unblock any of these:

- **Names** — bare `name`, `full_name`, `first_name`/`last_name`, `surname`, `customer_name`, etc. (non-personal `*_name` columns such as `table_name`, `file_name`, `product_name`, `username` are allowed)
- **Contact & government IDs** — email, SSN/social security, tax/VAT number, passport, national/identity number, driver's licence, voter ID
- **Demographics / special category** — sex, gender, race, ethnicity, religion, nationality, citizenship, marital status, sexual orientation, political/trade-union affiliation
- **Dates of birth & age** — DOB, birthday, birth year, age
- **Address & location** — street, postal/zip code, city, province, latitude/longitude, GPS, coordinates
- **Device & online identifiers** — IP/MAC address, device ID, IMEI, fingerprint, biometric
- **Financial** — credit/debit card, card number, IBAN, SWIFT, bank/account number, routing/sort code, CVV
- **Identifying media** — photo, avatar, profile picture, selfie, signature
- **Credentials & secrets** — password (and hashes), API key, access/refresh/session tokens, private keys, client secret, OTP

### The only overridable field: mobile / phone number

The single identifier the override applies to is the user's **mobile / phone number** — this is the username on Helium. When `allow_access_to_pii_data` is enabled for a tool, mobile/phone columns (e.g. `mobile`, `mobile_number`, `phone`, `msisdn`, `cellphone`) become selectable. Everything else — health data, wildcards, and all other PII — stays blocked.

```toml
[[tools]]
name = "execute_sql"
source = "production"
allow_access_to_pii_data = true   # unblocks the mobile/phone username ONLY; all other PII and health data stay hard-excluded
```

By default (`allow_access_to_pii_data = false`) even the mobile/phone number is blocked. Heuristics are name-based and may block or allow incorrectly for unusual schemas; narrow projections or opt in only with explicit policy.

### Error shape

When a query is blocked, the tool returns an error with code **`PII_ACCESS_VIOLATION`**, including:

- **Reason**: `clinical_health_data_blocked` (health data), `hard_pii_blocked` (names/email/national IDs/DOB/address/etc.), or `wildcard_clinical_risk` (wildcards) — all non-overridable; or `suspected_pii_or_clinical_column` for the overridable mobile/phone number when access is not enabled
- **Matched identifiers** (capped list), when applicable
- **What to do**: Remove health and personal columns and wildcards from the `SELECT`/`RETURNING` list. Only the mobile/phone username can be permitted, via `allow_access_to_pii_data = true`, after explicit policy approval.

**Configuration:** [TOML](/config/toml#allow_access_to_pii_data) `allow_access_to_pii_data`, or in single-DSN mode `ALLOW_ACCESS_TO_PII_DATA` / bare `--allow-access-to-pii-data` (or `=true` / `1` / `yes`; see [command-line](/config/command-line#pii-guard-cli)). This flag unblocks only the mobile/phone username; health data, wildcards, and all other PII remain hard-excluded. HTTP API responses list the effective value per source under each tool object as `allow_access_to_pii_data`.

## Selective Tool Exposure

Control which tools are available for each database source. By default, both `execute_sql` and `search_objects` are enabled. You can:

- Disable built-in tools entirely
- Configure specific tools with custom settings
- Expose only custom tools for restricted access

**Example: Disable execute_sql, keep search_objects:**

```toml
[[sources]]
id = "production"
dsn = "postgres://..."

# Only enable search_objects - execute_sql will not be available
[[tools]]
name = "search_objects"
source = "production"
```

**Example: Read-only execute_sql with row limit:**

```toml
[[sources]]
id = "production"
dsn = "postgres://..."

[[tools]]
name = "execute_sql"
source = "production"
readonly = true
max_rows = 100

[[tools]]
name = "search_objects"
source = "production"
```

<Note>
If no `[[tools]]` entries are defined for a source, both `execute_sql` and `search_objects` are enabled by default for backward compatibility.
</Note>
